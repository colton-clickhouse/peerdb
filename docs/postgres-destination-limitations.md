# Postgres destinations: known limitations and migration steps

What a CDC mirror into Postgres does not do, by design, and what to do instead. Most of it matters at cutover,
when the target becomes the primary. Mirrors from MySQL sources are the main case; Postgres and CockroachDB
sources are named where they differ.

## Not replicated

### TRUNCATE

A `TRUNCATE` on the source is not replicated, from any source: the target keeps the rows. Postgres sources publish
truncates, and the reader skips them ("Unhandled message type"); MySQL logs `TRUNCATE TABLE` as a statement, which
the reader ignores.

- Avoid `TRUNCATE` on replicated tables during a migration. Use `DELETE`, or resync the table afterwards.
- Partitions: truncating one partition of a replicated partitioned table is not replicated either.

### Source DDL other than ADD COLUMN

`ALTER TABLE ... ADD COLUMN` is replicated (see "Columns added mid-stream"). Other DDL is not: dropping, renaming or
changing the type of a column, indexes, constraints.

- **A column's type change** (`MODIFY COLUMN n VARCHAR(30)` on MySQL) keeps the mirror on the old type. Into
  Postgres, the first value the old type can't read fails normalize with an error naming the table (invalid input
  for the column's type), and the mirror alerts (see "Mirror health"); no value arrives changed. Into ClickHouse,
  check the values: resync the table after a type change.
- **Other DDL:** apply it to the target yourself, or resync the table.

### Column defaults and identity columns

Tables are created without the source's column defaults and without identity columns: they would act only after
cutover (normalize writes every column), and the sequence state at cutover is the application's.

Before cutover:

```sql
-- defaults, per column, as on the source
ALTER TABLE t ALTER COLUMN qty SET DEFAULT 5;
ALTER TABLE t ALTER COLUMN created_at SET DEFAULT now();
-- AUTO_INCREMENT / SERIAL keys: an identity, started above the highest replicated value
ALTER TABLE t ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
SELECT setval(pg_get_serial_sequence('t', 'id'), (SELECT coalesce(max(id), 0) + 1 FROM t), false);
```

An identity needs a `NOT NULL` integer column: `bigint`, not `numeric(20,0)` (see "Type mapping").

### Generated columns

Generated columns arrive as ordinary columns with their values. Postgres sources send no values for them through
CDC before Postgres 18 (`publish_generated_columns`), so rows changed through CDC hold NULL there. Exclude them from
the mirror and add them on the target as generated columns, or recompute them after cutover.

## Columns added mid-stream

`ADD COLUMN` is replicated, with the column nullable and PeerDB's default type for it.

- **Existing rows** get the source's default, as on the source, when it's a literal (`DEFAULT 'x'`, `DEFAULT 5`).
  The target column keeps no default (see above). A time default (`DEFAULT CURRENT_TIMESTAMP`) isn't carried: it
  would fill the time of the replay, not the source's, so those rows hold NULL.
- **Another type than PeerDB's** (an `INT UNSIGNED` that needs `bigint`, a `TIME` that needs `interval`): add the
  column on the target first, with that type. The replay keeps an existing column, and normalize casts to it.

## Type mapping

PeerDB creates each column with a default type for the source's type. Where that can't hold the source's values,
give the column another type with a column setting (`destination_type`), at mirror creation; the UI offers the
choices per column. Postgres destinations accept:

| PeerDB type | Default | `destination_type` |
|---|---|---|
| `INT UNSIGNED`, `MEDIUMINT UNSIGNED` (UInt32) | `integer` | `bigint`, `numeric` |
| `BIGINT UNSIGNED` (UInt64) | `bigint` | `numeric(20,0)`, `numeric` |
| `SMALLINT UNSIGNED` (UInt16), other integers | per size | wider integers, `numeric` |
| MySQL `TIME` | `time` (a time of day) | `interval` (MySQL's `TIME` is a duration: -838:59:59 to 838:59:59) |
| MySQL `TINYINT(1)` | `boolean` | `smallint`: read as an integer, so 2, 127 and -5 keep their values |
| `FLOAT` (real) | `real` | `float8` |
| text | `text` | `citext` (the extension must exist on the target) |
| `JSON` | `json` | `jsonb` |

Mirror validation refuses other choices, naming the column. A target table pre-created by the user is kept as it
is; normalize casts to its columns' types, for any type the values cast to.

Values PeerDB itself can't represent on Postgres:

- **MySQL zero dates**, with a zero month, day or year (`0000-00-00`, `2024-00-15`, `0000-05-10`), arrive as
  `1970-01-01`. A primary key holding one is refused, naming the column, since distinct keys would merge. Find them
  before a migration, per `DATE`/`DATETIME`/`TIMESTAMP` column: `SELECT count(*) FROM t WHERE CAST(col AS CHAR)
  LIKE '%-00%' OR CAST(col AS CHAR) LIKE '0000-%'`.
- **PostGIS SRIDs above 999999** are refused (PostGIS would store another SRID).

## Table and column names

Postgres truncates identifiers to 63 bytes. Mirror validation refuses names that Postgres would truncate: schemas,
tables and columns over 63 bytes, and mirror names whose raw table name (`_peerdb_raw_<mirror>`) or PeerDB's column
names would be.

Mirrors created before that check may already share a truncated raw table: two mirrors into one database whose
names share their first 51 bytes. One's raw-batch cleanup then deletes the other's rows before they're applied.
Find them in the catalog (mirrors whose destination is the same peer; peers that point at the same database by
other names need a manual check):

```sql
SELECT f.destination_peer, left('_peerdb_raw_' || lower(regexp_replace(f.name, '[^a-zA-Z0-9_]+', '_', 'g')), 63)
    AS raw_table, array_agg(f.name ORDER BY f.name) AS mirrors
FROM flows f JOIN peers p ON p.id = f.destination_peer
WHERE p.type = 3 AND f.query_string IS NULL
GROUP BY 1, 2 HAVING count(*) > 1;
```

Recreate all but one of each group under a shorter name. (Detecting this on running mirrors is a planned
follow-up.)

## Keyless tables

CDC applies changes by primary key, so tables without one are refused at validation for CDC mirrors into Postgres,
naming them, and so are mirrors that exclude a key column. Add a primary key on the source, or remove the table, or
use a snapshot-only mirror.

## Mirror health

A mirror that keeps failing with an error only the user can fix (a dropped target column, a missing publication or
slot, unsupported data, a connection problem) stays Running and retries. Once it has made no progress for
`PEERDB_STALLED_ALERT_THRESHOLD_MINUTES` (default 30, 0 disables), it logs a warning and alerts the configured
alert senders, once per alerting gap (`PEERDB_ALERTING_GAP_MINUTES`). The mirror status reports when it last made
progress and its last error.

- The latest error decides: one such error after a long run of transient ones (a network outage) alerts.
- There's no exact "failing since"; the mirror's error log has the history.

## Session settings and connection poolers

PeerDB pins the session settings that change values in text form (`extra_float_digits`, `IntervalStyle`, the time
zone and date style), whatever the source role or database sets. On the replication connection they're startup
parameters; on the others, `SET` after connecting, since pgbouncer refuses startup parameters it doesn't track.
Behind pgbouncer in transaction pooling, a `SET` reaches only one server connection: use session pooling for
PeerDB's peers.
