# Postgres destinations: known limitations and migration steps

What a CDC mirror into Postgres does not do, by design, and what to do instead. Most of it matters at cutover,
when the target becomes the primary. Mirrors from MySQL sources are the main case; Postgres and CockroachDB
sources are named where they differ.

## Not replicated

### TRUNCATE

A `TRUNCATE` on the source is not replicated, from any source: the target keeps the rows. Postgres sources publish
truncates, and the reader skips them ("Unhandled message type"); MySQL logs `TRUNCATE TABLE` as a statement, which
the reader ignores.

- Avoid `TRUNCATE` on replicated tables during a migration. Use `DELETE`, or resync the table afterwards.
- Partitions: truncating one partition of a replicated partitioned table is not replicated either.

### Source DDL other than ADD COLUMN

`ALTER TABLE ... ADD COLUMN` is replicated (see "Columns added mid-stream"). Other DDL is not: dropping, renaming or
changing the type of a column, indexes, constraints.

- **A column's type change** (`MODIFY COLUMN n VARCHAR(30)` on MySQL) keeps the mirror on the old type: the
  target column keeps its type, and CDC reads the new values as the old type (a resync reads the new one). The
  reader logs a warning ("column type change detected, not propagating"). Depending on the change, values:
  - **arrive changed, without an error:** a `DOUBLE` read as `FLOAT` is rounded to single precision; text read as
    an integer becomes 0 when it isn't a number and is clamped to the old type's range when it's too large, and
    read as `FLOAT`/`DOUBLE` becomes 0 when it isn't a number (a warning is logged once); `INT` to `INT UNSIGNED`
    (or back), and the other sizes, wrap around (`4294967295` arrives as `-1`, `-1` as `4294967295`); text read as a `TINYINT(1)` boolean
    is true only for `1`, `true`, `t`, `on` and `yes`, so `2` arrives as false;
  - **fail CDC** when the reader can't read the new values as the old type at all: an `INT` widened to `BIGINT`
    (an error naming the table and column), text read as a date or time that doesn't parse. The mirror retries and
    alerts (see "Mirror health");
  - **fail normalize** when the old type's values don't fit the target column (a pre-created column narrower than
    the new values).

  Check the source's DDL during a migration, and resync the table after a type change, into Postgres as into
  ClickHouse.
- **Other DDL:** apply it to the target yourself, or resync the table.

### Column defaults and identity columns

Tables are created without the source's column defaults and without identity columns: they would act only after
cutover (normalize writes every column), and the sequence state at cutover is the application's.

Before cutover:

```sql
-- defaults, per column, as on the source
ALTER TABLE t ALTER COLUMN qty SET DEFAULT 5;
ALTER TABLE t ALTER COLUMN created_at SET DEFAULT now();
-- AUTO_INCREMENT / SERIAL keys: an identity, started above the highest replicated value
ALTER TABLE t ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
SELECT setval(pg_get_serial_sequence('t', 'id'), (SELECT coalesce(max(id), 0) + 1 FROM t), false);
```

An identity needs a `NOT NULL` integer column: `bigint`, not `numeric(20,0)` (see "Type mapping").

### Generated columns

Generated columns arrive as ordinary columns with their values. Postgres sources send no values for them through
CDC before Postgres 18 (`publish_generated_columns`), so rows changed through CDC hold NULL there. Exclude them from
the mirror and add them on the target as generated columns, or recompute them after cutover.

## Columns added mid-stream

`ADD COLUMN` is replicated, with the column nullable and PeerDB's default type for it.

- **Existing rows** hold NULL in the new column on the target, even when the source column has a `DEFAULT`: MySQL
  fills the rows that predate the column without writing them to the binlog, so CDC never sees those values. Once
  the `ADD COLUMN` has replicated (the column exists on the target), backfill them with one `UPDATE`:

  ```sql
  -- source: ALTER TABLE orders ADD COLUMN status VARCHAR(10) NOT NULL DEFAULT 'new';
  UPDATE orders SET status = 'new' WHERE status IS NULL;
  ```

  Run it before CDC writes a real NULL into the column (a nullable column with a default can get one later), or
  limit it to the rows that predate the `ALTER` (for example by key). For a time default (`CURRENT_TIMESTAMP`),
  copy the values from the source by key instead: the source filled them at the `ALTER`'s time. The target
  column gets no default (see above).
- **Another type than PeerDB's** (an `INT UNSIGNED` that needs `bigint`, a `TIME` that needs `interval`): add the
  column on the target first, with that type. The replay keeps an existing column, and normalize casts to it.

## Type mapping

PeerDB creates each column with a default type for the source's type. Where that can't hold the source's values,
give the column another type with a column setting (`destination_type`). Column settings are set through the API
for now (a `columns` entry of the table mapping, by `source_name`); the mirror creation UI offers column types
for ClickHouse destinations only. They apply:

- on the Q type system only (the PG type system copies a Postgres source's types);
- where PeerDB creates the table: at mirror creation, for tables added to a mirror (with the added table's settings),
  and when a resync recreates the tables. A table that exists keeps its columns: a setting can't be changed on a
  running mirror's table (alter the target column yourself, normalize casts to it, or resync).

Postgres destinations accept:

| PeerDB type | Default | `destination_type` |
|---|---|---|
| `SMALLINT UNSIGNED` (UInt16) | `smallint` | `integer`, `bigint`, `numeric` |
| `INT UNSIGNED` (UInt32) | `integer` | `bigint`, `numeric` |
| `BIGINT UNSIGNED` (UInt64) | `bigint` | `numeric(20,0)`, `numeric` |
| other integers | per size | wider integers, `numeric` |
| MySQL `TIME` | `time` (a time of day) | `interval` (MySQL's `TIME` is a duration: -838:59:59 to 838:59:59) |
| CockroachDB `INTERVAL`, `INTERVAL[]` | `text` holding PeerDB's interval JSON | `interval`, `interval[]` (from the CockroachDB stack, below) |
| MySQL `TINYINT(1)` | `boolean` | `smallint`, `integer`, `bigint`: read as an integer, so 2, 127 and -5 keep their values |

The CockroachDB → Postgres fixes (stacked on these) add the `INTERVAL` choices to this list.

Unsigned integers get the signed type of the same size by default, which holds only half their range: a
`SMALLINT UNSIGNED` above 32767, an `INT UNSIGNED` above 2147483647 or a `BIGINT UNSIGNED` above
9223372036854775807 fails the snapshot or normalize (out of range). `TINYINT UNSIGNED` and `MEDIUMINT UNSIGNED` fit
their defaults (`smallint`, `integer`). Give the others a wider type where the values can exceed the signed range.

Mirror validation (and table creation, also with `skip_validation`) refuses other choices, naming the column. The
list holds only fixes for types that can't hold the source's values. Any other target type (`citext` for text,
`jsonb` for `JSON`, `double precision` for `FLOAT`, a domain) is a choice for the user to make by pre-creating the
target table: a pre-created table is kept as it is, and normalize casts to its columns' types, for any type the
values cast to. Such a type can change the values or how they compare: `citext` compares case-insensitively, so key
values that differ only in case collide on the target; `jsonb` doesn't keep the JSON's text (key order, whitespace,
duplicate keys); a `FLOAT` in `double precision` can show more digits than MySQL's. Known limits of pre-created
columns:

- **`bytea`** takes binary source columns only: a string, enum, JSON or UUID value fails normalize (`column ... is of
  type bytea but expression is of type text`).
- **`text` or `varchar`** for a non-string source column: CDC writes the value's text, but the initial snapshot can't
  write integer, floating-point or boolean columns into a text column (the snapshot fails), writes binary values
  raw, and writes dates and times in another format than CDC (`2024-02-29 00:00:00 +0000 UTC` instead of
  `2024-02-29`). Give such columns their default type for the snapshot and alter them afterwards, or check the
  values.
- **A domain** keeps its checks, the length of a domain over `varchar(n)` included: a value too long fails
  normalize rather than being cut.

Values PeerDB itself can't represent on Postgres:

- **MySQL zero dates**, with a zero month, day or year (`0000-00-00`, `2024-00-15`, `0000-05-10`), arrive as
  `1970-01-01` in mirrors created at or after InternalVersion 10 (`InternalVersion_MySQLZeroDatePartsAsZero`).
  Older mirrors keep their behaviour: `0000-00-00` arrives as `1970-01-01`, and a zero month or day as 01
  (`2024-00-15` arrives as `2024-01-15`). Tables whose primary key holds zero dates replicate, but keys that differ
  only in them (or from a real `1970-01-01`) become equal on the target: the snapshot fails with a duplicate key
  error, and in CDC the rows merge into one. Find them before a migration, per `DATE`/`DATETIME`/`TIMESTAMP` column:
  `SELECT count(*) FROM t WHERE CAST(col AS CHAR) LIKE '%-00%' OR CAST(col AS CHAR) LIKE '0000-%'`.
  A `DATE` or `DATETIME` partition column whose minimum or maximum isn't a real date makes the snapshot read the
  table as one partition. Incremental (or custom-query) QRep on such a watermark is refused
  (`WATERMARK_NOT_REAL_DATE`): use a watermark column with real dates, or a full-table refresh.
- **Geometry SRIDs** are kept (MySQL geometries, and Postgres sources' PostGIS values in the snapshot) in mirrors
  created at or after InternalVersion 11 (`InternalVersion_PgGeoKeepSRID`); there, SRIDs above 999999 are refused
  (PostGIS would store another SRID). Older mirrors drop the SRID (0). From that version on, the snapshot of a
  Postgres or CockroachDB source keeps the SRID too (it arrived as 0 in the snapshot, and with its SRID through CDC).
  A pre-created `geography` column takes geodetic SRIDs only (such as 4326): a projected one (3857) fails;
  transform on the source, or pre-create a `geometry` column.

## Table and column names

Postgres truncates identifiers to 63 bytes. Mirror validation refuses names that Postgres would truncate: schemas,
tables and columns over 63 bytes, and mirror names whose raw table name (`_peerdb_raw_<mirror>`) or PeerDB's column
names would be.

Mirrors created before that check may already share a truncated raw table: two mirrors into one database whose
names share their first 51 bytes. One's raw-batch cleanup then deletes the other's rows before they're applied.
Find them in the catalog (mirrors whose destination is the same peer; peers that point at the same database by
other names need a manual check):

```sql
SELECT f.destination_peer, left('_peerdb_raw_' || lower(regexp_replace(f.name, '[^a-zA-Z0-9_]+', '_', 'g')), 63)
    AS raw_table, array_agg(f.name ORDER BY f.name) AS mirrors
FROM flows f JOIN peers p ON p.id = f.destination_peer
WHERE p.type = 3 AND coalesce(f.query_string, '') = ''
GROUP BY 1, 2 HAVING count(*) > 1;
```

Recreate all but one of each group under a shorter name. (Detecting this on running mirrors is a planned
follow-up.)

## Keyless tables

CDC applies changes by primary key, so tables without one are refused at validation for CDC mirrors into Postgres,
naming them, and so are mirrors that exclude a key column. Add a primary key on the source, or remove the table, or
use a snapshot-only mirror. The exception is a Postgres source table with `REPLICA IDENTITY FULL` (below).

### Keyless REPLICA IDENTITY FULL tables (Postgres sources)

A Postgres table with no primary key and `REPLICA IDENTITY FULL` passes validation: PeerDB uses every column as
its key. The target table gets no key, and normalize matches rows on every column, using the changed row's new
values. That goes wrong in these cases:

- **Identical rows inserted in the same CDC batch collapse into one.** The initial snapshot copies duplicates
  correctly; the loss happens in CDC.
- **An `UPDATE` leaves the old row** next to the new one.
- **Deleting one of two identical rows removes both.**
- **A row containing a NULL is never matched:** deleting it does nothing, and updating it leaves the old row.
- **A `json` column fails normalize on every batch** (`could not identify an equality operator for type json`,
  SQLSTATE 42883). The table stops updating while the mirror stays Running. After the no-progress threshold the
  mirror warns and alerts (see "Mirror health"). A `jsonb` column fails differently: like any update, it leaves
  the old row.

Remedy: give the source table a key that CDC can use, then resync the table, so the target gets the key and loses
the duplicate and stale rows:

- a primary key; or
- a unique index on `NOT NULL` columns, with `ALTER TABLE ... REPLICA IDENTITY USING INDEX <index>`.

A fix in PeerDB is under discussion.

## Mirror health

A mirror that keeps failing with an error only the user can fix (a dropped target column, a missing publication or
slot, unsupported data, a connection problem) stays Running and retries. Once it has been failing, without progress,
for longer than `PEERDB_NO_PROGRESS_ALERT_THRESHOLD_MINUTES` (default 30, 0 disables), it logs a warning and alerts
the configured alert senders, once per alerting gap (`PEERDB_ALERTING_GAP_MINUTES`). The mirror status reports when
it last made progress, its last error (its snapshot's included), and whether it's failing without progress.

- A mirror paused while failing alerts on its first error after resuming; an idle mirror with an old error after its
  last progress alerts on its next one.
- Not covered: errors not classified as needing the user, failures that don't reach the mirror's error log, and a
  mirror that fails outright before the threshold.
- There's no exact "failing since"; the mirror's error log has the history.

## Session settings and connection poolers

PeerDB pins the session settings that change values in text form, whatever the source role or database sets:

- `extra_float_digits = 3`, `IntervalStyle = postgres` and `xmloption = content`: `SET` after connecting, on every
  connection including replication, since pgbouncer refuses startup parameters it doesn't track. The `SET`s are
  best-effort: where the server doesn't have or refuses one, PeerDB logs a warning and the connection goes on with
  the server's setting.
- the time zone (UTC) and `DateStyle` (`ISO, DMY`): startup parameters, which pgbouncer tracks.

Behind pgbouncer in transaction pooling, a `SET` reaches only the server connection it ran on, and PeerDB's later
statements can run on another one without it (PeerDB doesn't repeat them per transaction with `SET LOCAL`): use
session pooling for PeerDB's peers.
